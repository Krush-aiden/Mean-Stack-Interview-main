Q1. Design a URL Shortener service (like bit.ly) using Node.js.
Answer:
  Components:
    - API Layer: Express.js server with two endpoints:
        POST /shorten  → accepts long URL, returns short code
        GET /:code     → redirects to original URL
    - ID Generation: Use nanoid (7–8 chars) for a unique short code. Optionally use a counter-based Base62 encoding for predictable growth.
    - Storage: MongoDB or PostgreSQL to store { shortCode, originalUrl, createdAt, clickCount }.
    - Cache: Redis to cache shortCode → originalUrl lookups (TTL ~24h) so redirects don't hit DB on every request.
    - Rate Limiting: Apply per-IP rate limiting on POST /shorten to prevent abuse.
    - Analytics: On each GET, publish an event to a BullMQ queue to asynchronously increment click count — don't block the redirect.
  Scaling Considerations:
    - Horizontal scaling behind a load balancer (Nginx / AWS ALB).
    - DB read replicas for redirect lookups (read-heavy workload).
    - CDN for static assets if a dashboard is attached.

Q2. Design a real-time chat application using Node.js and WebSockets.
Answer:
  Components:
    - Transport: Socket.IO over WebSocket (with long-polling fallback).
    - Rooms: Socket.IO rooms map to chat channels/conversations.
    - Message Flow:
        1. Client emits "sendMessage" event with { roomId, text, senderId }.
        2. Server validates, persists to MongoDB (messages collection), then broadcasts to room.
    - Presence: Track online users in Redis (SET with TTL); broadcast "userOnline" / "userOffline" events.
    - Multiple Node instances: Use Socket.IO Redis Adapter so events are shared across all pods.
    - Auth: JWT validated on socket "connection" event via handshake query/headers.
    - Message history: REST endpoint GET /rooms/:id/messages with cursor-based pagination.
  Storage Schema:
    - messages: { _id, roomId, senderId, text, createdAt, readBy[] }
    - rooms:    { _id, name, members[], lastMessage, updatedAt }
  Scaling:
    - Sticky sessions OR Redis pub/sub adapter to handle multi-instance fan-out.
    - Store media files in S3; send pre-signed URLs rather than raw bytes through the socket.

Q4. Design a rate limiter for a public API in Node.js.
Answer:
  Algorithms:
    - Token Bucket:   Allow burst traffic; tokens replenish at a fixed rate. Good for general APIs.
    - Sliding Window Log: Precise, stores timestamps per request in Redis sorted set. Higher memory cost.
    - Sliding Window Counter: Approximation; blends current and previous window counts — low memory, fast.
  Implementation with Redis (Sliding Window Counter):
    - Key: "ratelimit:<userId>:<windowStart>"
    - On each request:
        1. INCR the key, set TTL = window size (e.g. 60s).
        2. Blend: count = current_window + (previous_window * overlap_fraction).
        3. If count > limit → return 429 Too Many Requests with Retry-After header.
  Express Middleware:
    - Attach as middleware per-route or globally.
    - Use ioredis pipeline for atomic INCR + EXPIRE to avoid race conditions.
    - For distributed systems, use a single Redis cluster (or Lua script for atomicity).
  Headers to return:
    - X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset

Q5. Design a notification system (email, push, SMS) for a large-scale app.
Answer:
  Flow:
    1. Producer (Order Service, User Service) publishes events to a message queue (BullMQ / Kafka).
       e.g.  { type: "ORDER_SHIPPED", userId, orderId, channel: ["email","push"] }
    2. Notification Worker consumes events, looks up user preferences/device tokens.
    3. Workers dispatch via:
       - Email:  SendGrid / AWS SES
       - Push:   Firebase Cloud Messaging (FCM)
       - SMS:    Twilio
  Reliability:
    - Dead Letter Queue (DLQ): Failed jobs moved to DLQ after 3 retries with exponential backoff.
    - Idempotency: Store notificationId in DB; skip if already sent.
    - Acknowledgement: Mark job done only after provider confirms delivery.
  Scalability:
    - Multiple worker replicas; horizontal scaling driven by queue depth (KEDA on Kubernetes).
    - Separate queues per channel (email-queue, sms-queue) so a slow SMS provider doesn't block emails.
  User Preferences:
    - Respect opt-out flags per channel per notification type stored in DB.
    - Batch digest: for low-priority events, aggregate and send once per hour.

Q6. How would you design a file upload service that handles large files?
Answer:
  Direct upload to S3 (recommended, bypasses your server):
    1. Client requests a pre-signed PUT URL from your API (POST /upload/presign).
    2. API generates URL using AWS SDK (expires in 15 min, scoped to specific key).
    3. Client uploads file directly to S3 using the pre-signed URL.
    4. S3 triggers a Lambda / SNS notification → your API records metadata in DB.
  Multipart upload (files > 100 MB):
    - Client splits file into parts (5 MB minimum each).
    - Initiates multipart upload → gets UploadId.
    - Uploads each part in parallel → collects ETags.
    - Completes multipart upload → S3 assembles the file.
  Post-upload processing (thumbnails, virus scan, transcoding):
    - S3 event triggers a BullMQ job / Lambda.
    - Worker processes file asynchronously, updates DB with status.
  Security:
    - Pre-signed URL scoped to exact file size (ContentLengthRange condition).
    - Validate file type by reading magic bytes server-side, not just extension.
    - Store files with randomized keys (UUID), not original file names.
    - Enable S3 server-side encryption (SSE-S3 or SSE-KMS).

Q7. Design a caching strategy for a high-traffic Node.js API.
Answer:
  Layers of caching:
    1. CDN (CloudFront / Cloudflare): Cache static assets and public GET responses at edge.
    2. HTTP Cache Headers: Set Cache-Control, ETag, Last-Modified on responses for client/proxy caching.
    3. Application Cache (Redis): Cache-aside pattern for DB query results.
       - On GET: check Redis → if miss, query DB, store result in Redis with TTL.
       - On write (POST/PUT/DELETE): invalidate or update relevant cache keys.
    4. In-Process Cache (node-cache / LRU cache): For extremely hot data (e.g. config, feature flags) — avoid Redis round-trip.
  Cache invalidation strategies:
    - TTL-based expiry: Simple, may serve stale data briefly. OK for product listings.
    - Event-driven invalidation: On data change, publish an event → cache layer deletes keys. More precise.
    - Write-through: Update cache on every write. Keeps cache warm but adds write latency.
  Pitfalls to avoid:
    - Cache stampede: Use probabilistic early expiry or a lock (Redlock) to prevent thundering herd.
    - Caching non-deterministic or user-specific data without namespacing keys per user.
    - Forgetting to set TTL (memory leak in Redis).

Q8. How would you handle database migrations in a production Node.js application?
Answer:
  Tool: Use a migration library — Knex.js migrations (SQL) or Mongoose migrate (NoSQL).
  Principles:
    - Migrations are versioned, sequential files committed to Git alongside code.
    - Each migration has an up() and down() (rollback) function.
    - Never modify an already-applied migration — create a new one.
  Zero-downtime migrations (Blue-Green / Rolling deployment):
    Step 1 — Expand:  Add new column/index as nullable. Deploy code that writes to both old and new columns.
    Step 2 — Migrate: Backfill data in batches (don't lock the table). CREATE INDEX CONCURRENTLY in Postgres.
    Step 3 — Contract: Remove old column once all traffic uses the new schema.
  CI/CD integration:
    - Run migrations as a pre-deploy step (separate container/job).
    - Gate deployment on migration success — rollback if it fails.
    - Store migration state in a migrations table in the DB (not in the filesystem).
  Safety rules:
    - Never DROP COLUMN or rename in the same deploy as the code change.
    - Test rollback (down()) in staging before production.
    - Take a DB snapshot before large migrations.

-- middleware/validateTask.js --

  const { VALID_STATUSES } = require('../models/task');

  function validateTask(req, res, next) {
    const { title, status } = req.body;
    if (!title || typeof title !== 'string' || !title.trim()) {
      return res.status(400).json({ message: 'title is required and must be a non-empty string' });
    }
    if (status && !VALID_STATUSES.includes(status)) {
      return res.status(400).json({ message: `status must be one of: ${VALID_STATUSES.join(', ')}` });
    }
    next();
  }

  module.exports = { validateTask };


-- controllers/taskController.js --

  const { tasks, uuidv4 } = require('../models/task');

  // GET /tasks  — optional ?status= filter (bonus)
  function getAllTasks(req, res) {
    const { status } = req.query;
    const result = status ? tasks.filter(t => t.status === status) : tasks;
    res.status(200).json(result);
  }

  // GET /tasks/:id
  function getTaskById(req, res) {
    const task = tasks.find(t => t.id === req.params.id);
    if (!task) return res.status(404).json({ message: 'Task not found' });
    res.status(200).json(task);
  }

  // POST /tasks
  function createTask(req, res) {
    const { title, description = '', status = 'todo' } = req.body;
    const task = { id: uuidv4(), title: title.trim(), description, status, createdAt: new Date().toISOString() };
    tasks.push(task);
    res.status(201).json(task);
  }

  // PATCH /tasks/:id
  function updateTask(req, res) {
    const task = tasks.find(t => t.id === req.params.id);
    if (!task) return res.status(404).json({ message: 'Task not found' });

    const { title, description, status } = req.body;
    if (title !== undefined) task.title = title.trim();
    if (description !== undefined) task.description = description;
    if (status !== undefined) task.status = status;

    res.status(200).json(task);
  }

  // DELETE /tasks/:id
  function deleteTask(req, res) {
    const index = tasks.findIndex(t => t.id === req.params.id);
    if (index === -1) return res.status(404).json({ message: 'Task not found' });
    tasks.splice(index, 1);
    res.status(204).send();
  }

  module.exports = { getAllTasks, getTaskById, createTask, updateTask, deleteTask };
