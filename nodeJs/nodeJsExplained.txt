### 1. What is the event loop in Node.js? & JavaScript.

- **How it works**: The event loop continuously checks the call stack and the callback queue. If the call stack is empty, it takes the first callback from the queue and pushes it onto the call stack for execution.
- **Components**: Call stack, callback queue, microtask queue, and the event loop itself.
- **Example**: When you perform an asynchronous operation like reading a file, the event loop allows other code to run while waiting for the file operation to complete.

### 12. How does Node.js handle asynchronous operations?
Node.js handles asynchronous operations using the event loop, callbacks, promises, and async/await.

**Asynchronous Operations**:
- **Event Loop**: Continuously checks the call stack and callback queue, executing callbacks when the call stack is empty.
- **Callbacks**: Functions passed as arguments to other functions, executed after the completion of asynchronous operations.
- **Promises**: Objects representing the eventual completion or failure of an asynchronous operation, providing `.then()` and `.catch()` methods.
- **Async/Await**: Syntactic sugar over promises, allowing asynchronous code to be written in a synchronous style.

**Example**:
```javascript
// Using a callback
fs.readFile('file.txt', (err, data) => {
  if (err) throw err;
  console.log(data.toString());
});

// Using a promise
fs.promises.readFile('file.txt')
  .then(data => console.log(data.toString()))
  .catch(err => console.error(err));

// Using async/await
async function readFile() {
  try {
    const data = await fs.promises.readFile('file.txt');
    console.log(data.toString());
  } catch (err) {
    console.error(err);
  }
}
readFile();
```

### 14. What is the difference between process.nextTick() and setImmediate()?
Both `process.nextTick()` and `setImmediate()` are used to schedule callbacks in Node.js, but they have different timing characteristics.

**process.nextTick()**:
- Executes the callback after the current operation completes, before the event loop continues.
- Higher priority than `setImmediate()`.
- Used for deferring execution to the next iteration of the event loop.

**setImmediate()**:
- Executes the callback after the current event loop phase completes.
- Lower priority than `process.nextTick()`.
- Used for deferring execution to the next iteration of the event loop, but after I/O events.

**Example**:
```javascript
console.log('Start');

process.nextTick(() => {
  console.log('Next Tick');
});

setImmediate(() => {
  console.log('Immediate');
});

console.log('End');
```
**Output**:
```
Start
End
Next Tick
Immediate
```

### 16. What is middleware in Express.js?
**Middleware** in Express.js is a function that has access to the request object (`req`), the response object (`res`), and the next middleware function in the application’s request-response cycle.

**Purpose of Middleware**:
- Execute any code.
- Make changes to the request and response objects.
- End the request-response cycle.
- Call the next middleware function.

**Types of Middleware**:
- **Application-Level Middleware**: Bound to an instance of `express()`.
- **Router-Level Middleware**: Bound to an instance of `express.Router()`.
- **Error-Handling Middleware**: Takes four arguments (err, req, res, next).
- **Built-In Middleware**: Provided by Express (e.g., `express.json()`, `express.static()`).
- **Third-Party Middleware**: Installed via npm (e.g., `body-parser`, `morgan`).

**Example**:
```javascript
const express = require('express');
const app = express();

// Application-Level Middleware
app.use((req, res, next) => {
  console.log('Time:', Date.now());
  next();
});

// Router-Level Middleware
const router = express.Router();
router.use((req, res, next) => {
  console.log('Request URL:', req.originalUrl);
  next();
});
app.use('/user', router);

// Error-Handling Middleware
app.use((err, req, res, next) => {
  console.error(err.stack);
  res.status(500).send('Something broke!');
});

app.listen(3000, () => {
  console.log('Server is running on port 3000');
});
```

```javascript
const writableStream = fs.createWriteStream('output.txt');
```

### 20. How does Node.js handle multi-threading?
Node.js is single-threaded by design, using an event-driven, non-blocking I/O model. However, it can handle multi-threading through the use of worker threads and the `cluster` module.

**Multi-Threading in Node.js**:
- **Event Loop**: The main thread runs the event loop, handling asynchronous operations.
- **Worker Threads**: Introduced in Node.js v10.5.0, worker threads allow for parallel execution of JavaScript code.
- **Cluster Module**: Allows you to create child processes (workers) that share the same server port, enabling load balancing across multiple CPU cores.

**Example using Worker Threads**:
```javascript
const { Worker, isMainThread, parentPort } = require('worker_threads');

if (isMainThread) {
  // Main thread
  const worker = new Worker(__filename);
  worker.on('message', message => console.log(message));
} else {
  // Worker thread
  parentPort.postMessage('Hello from worker thread');
}
```

**Example using Cluster Module**:
```javascript
const cluster = require('cluster');
const http = require('http');
const numCPUs = require('os').cpus().length;

if (cluster.isMaster) {
  // Fork workers
  for (let i = 0; i < numCPUs; i++) {
    cluster.fork();
  }

  cluster.on('exit', (worker, code, signal) => {
    console.log(`Worker ${worker.process.pid} died`);
  });
} else {
  // Workers can share any TCP connection
  http.createServer((req, res) => {
    res.writeHead(200);
    res.end('Hello, World!\n');
  }).listen(8000);
}
```

### 25. What is the difference between PUT & POST?
Both PUT and POST are HTTP methods used to send data to the server, but they have different semantics.

**PUT**:
- **Idempotent**: Multiple identical requests should have the same effect as a single request.
- **Update or Create**: Used to update a resource or create it if it does not exist.
- **Full Replacement**: Typically replaces the entire resource.

**POST**:
- **Non-Idempotent**: Multiple identical requests may have different effects.
- **Create**: Used to create a new resource.
- **Partial Update**: Can be used to send partial data to update a resource.

**Example**:
```javascript
// PUT /users/1
app.put('/users/1', (req, res) => {
  const updatedUser = req.body;
  // Update user in database
  res.json(updatedUser);

  const newUser = req.body;
  // Add user to database
  res.status(201).json(newUser);
```

### 26. What is Content Negotiation?
**Content Negotiation** is a mechanism defined in HTTP that makes it possible to serve different representations of a resource at the same URI. The client specifies its preferences using headers, and the server selects the appropriate representation.

**Common Headers for Content Negotiation**:
- **Accept**: Specifies the media types the client can process (e.g., `application/json`, `text/html`).
- **Accept-Language**: Specifies the preferred languages (e.g., `en-US`, `fr`).
- **Accept-Encoding**: Specifies the preferred content encodings (e.g., `gzip`, `deflate`).

**Example**:
```javascript
app.get('/data', (req, res) => {

    res.json({ message: 'Hello, JSON!' });

    res.send('<p>Hello, HTML!</p>');
  } else {
    res.type('text').send('Hello, Text!');
  }
});
```

### 30. Explain HTTP methods.
HTTP methods are used to perform actions on resources in a web server. The most common HTTP methods are:

- **GET**: Retrieves data from the server. It is a read-only operation and does not modify the resource.
  ```http
  GET /users
  ```

- **POST**: Sends data to the server to create a new resource.
  ```http
  POST /users
  ```

- **PUT**: Updates an existing resource or creates a new resource if it does not exist. It is idempotent, meaning multiple identical requests have the same effect as a single request.
  ```http
  PUT /users/1
  ```

- **DELETE**: Deletes a resource from the server.
  ```http
  DELETE /users/1
  ```

- **PATCH**: Partially updates an existing resource.
  ```http
  PATCH /users/1
  ```

- **HEAD**: Similar to GET, but it only retrieves the headers and not the body of the response.
  ```http
  HEAD /users
  ```

- **OPTIONS**: Describes the communication options for the target resource.
  ```http
  OPTIONS /users
  ```

### 31. Explain HTTP codes.
HTTP status codes are issued by a server in response to a client's request. They indicate whether the request was successful or if there was an error.

**Common HTTP Status Codes**:
- **1xx (Informational)**:
  - `100 Continue`: The server has received the request headers and the client should proceed to send the request body.

- **2xx (Success)**:
  - `200 OK`: The request was successful.
  - `201 Created`: The request was successful and a new resource was created.
  - `204 No Content`: The request was successful but there is no content to send in the response.

- **3xx (Redirection)**:
  - `301 Moved Permanently`: The resource has been moved to a new URL permanently.
  - `302 Found`: The resource has been moved to a new URL temporarily.

- **4xx (Client Error)**:
  - `400 Bad Request`: The server could not understand the request due to invalid syntax.
  - `401 Unauthorized`: The client must authenticate itself to get the requested response.
  - `403 Forbidden`: The client does not have access rights to the content.
  - `404 Not Found`: The server cannot find the requested resource.

- **5xx (Server Error)**:
  - `500 Internal Server Error`: The server encountered an unexpected condition.
  - `502 Bad Gateway`: The server received an invalid response from the upstream server.

### 44. Implementation of debounce & throttling
**Debounce** and **throttling** are techniques used to control the rate at which a function is executed.

**Debounce**:
- Ensures that a function is only executed after a specified delay has passed since the last time it was invoked.
- Useful for scenarios like search input where you want to wait until the user has stopped typing.

**Example**:
```javascript
function debounce(func, delay) {
  let timeoutId;
  return function(...args) {
    clearTimeout(timeoutId);
    timeoutId = setTimeout(() => {
      func.apply(this, args);
    }, delay);
  };
}

const debouncedFunction = debounce(() => {
  console.log('Debounced function executed');
}, 300);

window.addEventListener('resize', debouncedFunction);
```

**Throttling**:
- Ensures that a function is only executed once in a specified interval, regardless of how many times it is invoked.
- Useful for scenarios like window resizing or scrolling where you want to limit the rate of execution.

**Example**:
```javascript
function throttle(func, interval) {
  let lastTime = 0;
  return function(...args) {
    const now = Date.now();
    if (now - lastTime >= interval) {
      lastTime = now;
      func.apply(this, args);
    }
  };
}

const throttledFunction = throttle(() => {
  console.log('Throttled function executed');
}, 300);

window.addEventListener('scroll', throttledFunction);
```

### 47. Explain backpressure in Node.js streams. How does Node handle it?
**Backpressure** occurs when a writable stream cannot process data as fast as a readable stream produces it. Without handling backpressure, data piles up in memory and can crash the application.

**How Node.js handles it:**
- When you call `writable.write(chunk)`, it returns `false` if the internal buffer is full.
- The readable stream should pause and wait for the `'drain'` event before sending more data.
- `stream.pipeline()` handles backpressure automatically (preferred over `.pipe()`).

**Example — Manual backpressure handling:**
```javascript
const fs = require('fs');
const readable = fs.createReadStream('largefile.txt');
const writable = fs.createWriteStream('output.txt');

readable.on('data', (chunk) => {
  const canContinue = writable.write(chunk);
  if (!canContinue) {
    readable.pause(); // Stop reading until drain
  }
});

writable.on('drain', () => {
  readable.resume(); // Resume reading
});

readable.on('end', () => {
  writable.end();
});
```

**Example — Using pipeline (recommended):**
```javascript
const { pipeline } = require('stream/promises');
const fs = require('fs');
const zlib = require('zlib');

await pipeline(
  fs.createReadStream('input.txt'),
  zlib.createGzip(),
  fs.createWriteStream('input.txt.gz')
);
// Backpressure handled automatically, errors propagated
```

### 48. How do Worker Threads differ from Child Processes? When to use each?
Both allow running code outside the main event loop, but they work differently:

**Worker Threads (`worker_threads` module):**
- Share the same process and memory space (can share ArrayBuffer via SharedArrayBuffer)
- Lightweight — lower overhead than spawning new processes
- Communicate via `parentPort.postMessage()` and `worker.postMessage()`
- **Use for:** CPU-intensive tasks (image processing, encryption, parsing large JSON)

**Child Processes (`child_process` module):**
- Spawn entirely new OS processes with separate memory
- Higher overhead but fully isolated
- Can run any system command or script (`exec`, `spawn`, `fork`)
- `fork()` creates a new Node.js process with IPC channel
- **Use for:** Running shell commands, executing separate scripts, full isolation needed

**Example — Worker Thread:**
```javascript
// main.js
const { Worker } = require('worker_threads');

const worker = new Worker('./heavy-task.js', {
  workerData: { iterations: 1000000 }
});

worker.on('message', (result) => console.log('Result:', result));
worker.on('error', (err) => console.error(err));

// heavy-task.js
const { workerData, parentPort } = require('worker_threads');
let sum = 0;
for (let i = 0; i < workerData.iterations; i++) { sum += i; }
parentPort.postMessage(sum);
```

**Example — Child Process:**
```javascript
const { fork } = require('child_process');
const child = fork('./child-script.js');

child.send({ task: 'processData' });
child.on('message', (result) => console.log('Child says:', result));
```

### 49. How would you implement graceful shutdown in a Node.js app?
**Graceful shutdown** means the server stops accepting new connections, finishes ongoing requests, closes database connections, and then exits cleanly.

**Why it matters:** In production (Docker, Kubernetes), your app receives SIGTERM before being killed. If you don't handle it, active requests get dropped.

```javascript
const express = require('express');
const mongoose = require('mongoose');

const app = express();
const server = app.listen(3000);

function gracefulShutdown(signal) {
  console.log(`${signal} received. Starting graceful shutdown...`);

  // 1. Stop accepting new connections
  server.close(() => {
    console.log('HTTP server closed.');

    // 2. Close database connections
    mongoose.connection.close(false, () => {
      console.log('MongoDB connection closed.');

      // 3. Close any other resources (Redis, message queues, etc.)
      process.exit(0);
    });
  });

  // 4. Force exit if graceful shutdown takes too long
  setTimeout(() => {
    console.error('Forced shutdown — timeout exceeded.');
    process.exit(1);
  }, 10000); // 10 second timeout
}

process.on('SIGTERM', () => gracefulShutdown('SIGTERM'));
process.on('SIGINT', () => gracefulShutdown('SIGINT'));
```

### 50. Explain the cluster module and how PM2 uses it in production.
The **cluster module** allows you to create multiple worker processes that share the same server port, utilizing all CPU cores.

**How it works:**
- The master process forks worker processes (one per CPU core).
- The OS distributes incoming connections across workers (round-robin on most platforms).
- If a worker crashes, the master can fork a new one.

**Example:**
```javascript
const cluster = require('cluster');
const os = require('os');
const express = require('express');

if (cluster.isMaster) {
  const numCPUs = os.cpus().length;
  console.log(`Master process ${process.pid} forking ${numCPUs} workers`);

  for (let i = 0; i < numCPUs; i++) {
    cluster.fork();
  }

  cluster.on('exit', (worker) => {
    console.log(`Worker ${worker.process.pid} died. Forking a new one.`);
    cluster.fork(); // Auto-restart
  });
} else {
  const app = express();
  app.get('/', (req, res) => res.send(`Worker ${process.pid}`));
  app.listen(3000);
}
```

**PM2 cluster mode:**
- PM2 abstracts all the above. You just run: `pm2 start app.js -i max`
- `-i max` = one worker per CPU core
- PM2 handles: auto-restart on crash, zero-downtime reload (`pm2 reload`), log management, monitoring

### 51. What is the difference between process.nextTick() and queueMicrotask()?
Both execute callbacks before the next event loop phase, but they have different priority:

| Feature | `process.nextTick()` | `queueMicrotask()` |
|---|---|---|
| Priority | Runs BEFORE microtasks (Promises) | Runs WITH microtasks (same queue as Promises) |
| When it runs | After current operation, before I/O | After current operation, after nextTick |
| Recursion risk | Can starve I/O if called recursively | Less likely to starve I/O |
| Standard | Node.js specific | Web standard (also works in browsers) |

**Execution order:**
```javascript
console.log('1 - start');

process.nextTick(() => console.log('2 - nextTick'));
queueMicrotask(() => console.log('3 - queueMicrotask'));
Promise.resolve().then(() => console.log('4 - Promise'));

console.log('5 - end');

// Output: 1 - start → 5 - end → 2 - nextTick → 3 - queueMicrotask → 4 - Promise
```

**Rule of thumb:** Use `queueMicrotask()` for standard-compliant code. Use `process.nextTick()` only when you need something to execute before all other microtasks.

```javascript
const Redis = require('ioredis');
const redis = new Redis();

async function slidingWindowRateLimit(req, res, next) {
  const key = `rate:${req.ip}`;
  const now = Date.now();
  const windowMs = 60 * 1000; // 1 minute
  const maxRequests = 60;

  // Remove old entries outside the window
  await redis.zremrangebyscore(key, 0, now - windowMs);

  // Count requests in current window
  const count = await redis.zcard(key);

  if (count >= maxRequests) {
    return res.status(429).json({ error: 'Rate limit exceeded' });
  }

  // Add current request
  await redis.zadd(key, now, `${now}-${Math.random()}`);
  await redis.expire(key, Math.ceil(windowMs / 1000));

  next();
}
```

### 59. What caching strategies can you use in a Node.js app?

| Strategy | How it works | Best for |
|---|---|---|
| **Cache-aside (Lazy)** | App checks cache first, loads from DB on miss, writes to cache | Most common, general purpose |
| **Write-through** | App writes to cache AND DB simultaneously | Data consistency matters |
| **Write-behind** | App writes to cache, cache writes to DB asynchronously | High write throughput |
| **Read-through** | Cache itself loads from DB on miss | Simplified app logic |

**Example — Cache-aside with Redis:**
```javascript
const Redis = require('ioredis');
const redis = new Redis();

async function getUser(userId) {
  // 1. Check cache
  const cached = await redis.get(`user:${userId}`);
  if (cached) return JSON.parse(cached);

  // 2. Cache miss — fetch from DB
  const user = await User.findById(userId);

  // 3. Store in cache with TTL
  await redis.set(`user:${userId}`, JSON.stringify(user), 'EX', 3600); // 1 hour

  return user;
}

// Invalidate cache on update
async function updateUser(userId, data) {
  await User.findByIdAndUpdate(userId, data);
  await redis.del(`user:${userId}`); // Invalidate
}
```

**Other caching layers:**
- **In-memory cache** (`node-cache`, `lru-cache`) — single instance, no network hop
- **HTTP caching** — ETags, Cache-Control headers
- **CDN caching** — Cloudflare, CloudFront for static assets
- **Database query cache** — MongoDB result caching

### 60. How would you implement a job queue in Node.js?
**Job queues** handle tasks that shouldn't block the request-response cycle: sending emails, processing images, generating reports.

**BullMQ (Redis-based) — Most popular in Node.js ecosystem:**
```javascript
// Setup
const { Queue, Worker } = require('bullmq');
const Redis = require('ioredis');
const connection = new Redis({ maxRetriesPerRequest: null });

// 1. Create a queue
const emailQueue = new Queue('emails', { connection });

// 2. Add jobs (from your API route)
app.post('/register', async (req, res) => {
  const user = await User.create(req.body);

  // Add email job — doesn't block the response
  await emailQueue.add('welcome-email', {
    to: user.email,
    name: user.name
  }, {
    attempts: 3,            // Retry 3 times on failure
    backoff: { type: 'exponential', delay: 2000 },
    removeOnComplete: true
  });

  res.status(201).json(user);
});

// 3. Process jobs (separate worker file or process)
const worker = new Worker('emails', async (job) => {
  console.log(`Sending ${job.name} to ${job.data.to}`);
  await sendEmail(job.data.to, job.data.name);
}, { connection, concurrency: 5 });

worker.on('completed', (job) => console.log(`Job ${job.id} completed`));
worker.on('failed', (job, err) => console.error(`Job ${job.id} failed:`, err));
```

**Other queue options:**
- **Agenda** — MongoDB-based (simpler, no Redis needed)
- **RabbitMQ / Kafka** — for complex event-driven architectures
- **AWS SQS** — fully managed, serverless

### 61. Explain the difference between pipeline() and .pipe() for streams.

| Feature | `.pipe()` | `pipeline()` |
|---|---|---|
| Error handling | Does NOT propagate errors | Propagates errors from any stream |
| Cleanup | Does NOT destroy streams on error | Destroys all streams on error |
| Return value | Returns destination stream | Returns Promise (with `stream/promises`) |
| Recommended | Legacy — avoid in new code | Yes — use this always |

**`.pipe()` problem:**
```javascript
// If readStream errors, writeStream stays open (resource leak)
readStream.pipe(writeStream);

// You have to manually handle errors on EVERY stream
readStream.on('error', handleError);
writeStream.on('error', handleError);
```

**`pipeline()` solution:**
```javascript
const { pipeline } = require('stream/promises');

try {
  await pipeline(readStream, transformStream, writeStream);
  console.log('Pipeline completed');
} catch (err) {
  console.error('Pipeline failed:', err);
  // All streams are automatically destroyed
}
```

### 62. What is the V8 garbage collector and how does it work?
V8 (Node.js's JavaScript engine) uses a **generational garbage collector** — it divides memory into generations based on object age.

**Heap structure:**
- **New Space (Young Generation):** Small (~1-8 MB). Newly created objects live here. Collected frequently.
- **Old Space (Old Generation):** Larger. Objects that survive 2 GC cycles in New Space are promoted here. Collected less frequently.

**GC Algorithms:**
1. **Scavenge (Minor GC):** Runs on New Space. Uses "semi-space" — copies live objects from one half to the other, dead objects are left behind. Very fast.
2. **Mark-Sweep (Major GC):** Runs on Old Space. Marks all reachable objects, sweeps (frees) unreachable ones.
3. **Mark-Compact:** Runs after Mark-Sweep. Compacts memory by moving objects together to reduce fragmentation.
4. **Incremental/Concurrent:** Major GC runs incrementally to avoid long pauses (important for server responsiveness).

**Practical impact:**
- Objects < 64KB → New Space → fast cleanup
- Long-lived objects → Old Space → more expensive to collect
- Avoid creating many short-lived large objects
- Monitor with `--trace-gc` flag or `v8.getHeapStatistics()`

### 63. How do you handle uncaught exceptions and unhandled rejections in production?

```javascript
// Catch synchronous errors that weren't caught anywhere

  // Log to external service (Sentry, Datadog, etc.)
  // Then EXIT — the process is in an undefined state
```

**Best practices:**
- **Always exit after uncaughtException** — the process state is unreliable
- Use PM2 or Docker to auto-restart the process
- Log errors to an external service BEFORE exiting
- The real fix: add proper try/catch and .catch() in your code
- Use Express error-handling middleware for route errors:
```javascript
app.use((err, req, res, next) => {
  console.error(err.stack);

    status: 'error',

  });

```

### 64. What are operational errors vs programmer errors? How do you handle each?

| Type | Examples | How to handle |
|---|---|---|
| **Operational** | DB connection timeout, invalid user input, file not found, API rate limited | Handle gracefully — retry, return error to client, use fallback |
| **Programmer** | TypeError, reading property of undefined, wrong function arguments | Fix the bug. Crash and restart in production. |

**Key distinction:** Operational errors are expected — they happen in production. Programmer errors are bugs — they shouldn't happen.

```javascript
// Custom operational error class
class AppError extends Error {
  constructor(message, statusCode) {
    super(message);
    this.statusCode = statusCode;
    this.isOperational = true; // Flag to distinguish
    Error.captureStackTrace(this, this.constructor);
  }
}

// In error handler middleware
app.use((err, req, res, next) => {
  if (err.isOperational) {
    // Known error — send clean response to client
    return res.status(err.statusCode).json({ message: err.message });
  }
  // Programmer error — log and crash
  console.error('PROGRAMMER ERROR:', err);
  process.exit(1); // PM2 will restart
});
```

### 68. Explain refresh token rotation and reuse detection.
**Problem:** Access tokens expire quickly (15 min). Users shouldn't re-login every 15 minutes.
**Solution:** Refresh tokens — longer-lived tokens used to get new access tokens.

**Refresh Token Rotation:**
- Every time a refresh token is used, issue a NEW refresh token and invalidate the old one.
- This limits the window of vulnerability if a refresh token is stolen.

**Reuse Detection:**
- If someone tries to use an already-rotated (old) refresh token, it means the token was stolen.
- Immediately invalidate ALL refresh tokens for that user (force re-login).

```javascript
// Token refresh endpoint
app.post('/auth/refresh', async (req, res) => {
  const { refreshToken } = req.body;

  // 1. Find stored token in DB
  const storedToken = await RefreshToken.findOne({ token: refreshToken });

  if (!storedToken) {
    return res.status(401).json({ error: 'Invalid refresh token. Please login again.' });
  }

  if (storedToken.isUsed) {
    // REUSE DETECTED — someone stole the old token
    await RefreshToken.deleteMany({ userId: storedToken.userId });
    return res.status(401).json({ error: 'Security breach. All sessions revoked.' });
  }

  // 2. Mark current token as used
  storedToken.isUsed = true;
  await storedToken.save();

  // 3. Issue new tokens
  const newAccessToken = generateAccessToken(storedToken.userId);
  const newRefreshToken = crypto.randomBytes(64).toString('hex');

  await RefreshToken.create({
    token: newRefreshToken,
    userId: storedToken.userId,
    expiresAt: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000) // 7 days
  });

  res.json({ accessToken: newAccessToken, refreshToken: newRefreshToken });
});
```

### 69. What is RBAC (Role-Based Access Control)? How to implement in Express?
**RBAC** restricts access based on user roles. Each role has a set of permissions.

**Simple RBAC middleware:**
```javascript
// Define roles and permissions
const permissions = {
  admin: ['read', 'write', 'delete', 'manage_users'],
  restaurant_owner: ['read', 'write', 'manage_menu'],
  customer: ['read', 'place_order'],
};

// Middleware factory
function authorize(...requiredPermissions) {
  return (req, res, next) => {
    const userRole = req.user.role; // Set by auth middleware
    const userPermissions = permissions[userRole] || [];

    const hasPermission = requiredPermissions.every(
      (perm) => userPermissions.includes(perm)
    );

    if (!hasPermission) {
      return res.status(403).json({ error: 'Insufficient permissions' });
    }
    next();
  };
}

// Usage in routes
app.delete('/api/restaurants/:id',
  authenticate,                    // Verify JWT
  authorize('delete'),             // Check permission
  restaurantController.delete
);

app.post('/api/menu',
  authenticate,
  authorize('manage_menu'),
  menuController.create
);
```

### 71. Explain cursor-based pagination vs offset-based. When to use each?

**Offset-based:** `GET /api/items?page=3&limit=20` → `skip(40).limit(20)`
| Pros | Cons |
|---|---|
| Simple to implement | Slow on large datasets (skip scans rows) |
| Can jump to any page | Inconsistent if data changes between pages |

**Cursor-based:** `GET /api/items?cursor=abc123&limit=20`
| Pros | Cons |
|---|---|
| Consistent results even if data changes | Can't jump to arbitrary pages |
| Performance stays constant regardless of position | Slightly more complex |

```javascript
// Cursor-based pagination
app.get('/api/orders', async (req, res) => {
  const { cursor, limit = 20 } = req.query;
  const query = cursor
    ? { _id: { $gt: cursor } }  // Get items AFTER cursor
    : {};

  const orders = await Order.find(query)
    .sort({ _id: 1 })
    .limit(parseInt(limit) + 1);  // Fetch one extra to check hasMore

  const hasMore = orders.length > limit;
  if (hasMore) orders.pop();  // Remove the extra

  res.json({
    data: orders,
    nextCursor: hasMore ? orders[orders.length - 1]._id : null,
    hasMore
  });
});
```

**When to use which:**
- Offset → admin panels, small datasets, need page numbers
- Cursor → infinite scroll, large datasets, real-time feeds, APIs

### 72. What is IDOR (Insecure Direct Object Reference) and how to prevent it?
**IDOR** is a vulnerability where a user can access other users' data by modifying a parameter (like an ID in the URL).

**Vulnerable code:**
```javascript
// Anyone with a valid JWT can access ANY user's orders by changing the ID
app.get('/api/orders/:orderId', authenticate, async (req, res) => {
  const order = await Order.findById(req.params.orderId); // ← No ownership check!
  res.json(order);
});
```

**Secure code:**
```javascript
app.get('/api/orders/:orderId', authenticate, async (req, res) => {
  const order = await Order.findOne({
    _id: req.params.orderId,
    userId: req.user._id  // ← Only return if the order belongs to this user
  });

  if (!order) return res.status(404).json({ error: 'Order not found' });
  res.json(order);
});
```

**Prevention strategies:**
- Always verify resource ownership in queries
- Use middleware for authorization checks
- Avoid exposing sequential IDs (use UUIDs)
- Test with different user accounts

### 73. How do you validate request body/query/params? (Joi, Zod)

### 74. Explain the Circuit Breaker pattern for external API calls.
**Problem:** If a third-party API (payment gateway, email service) is down, your app keeps sending requests, wasting resources and slowing down.

**Circuit Breaker states:**
1. **CLOSED** (normal) — Requests flow through. Track failures.
2. **OPEN** (tripped) — After N failures, stop sending requests. Return error immediately.
3. **HALF-OPEN** (testing) — After a timeout, allow one test request. If it succeeds → CLOSED. If it fails → OPEN.

```javascript
// Using opossum (Node.js circuit breaker library)
const CircuitBreaker = require('opossum');

const paymentService = async (orderData) => {
  return axios.post('https://payment-api.com/charge', orderData);
};

const breaker = new CircuitBreaker(paymentService, {
  timeout: 5000,         // If function takes > 5s, trigger failure
  errorThresholdPercentage: 50,  // Open circuit if 50% requests fail
  resetTimeout: 30000,   // Try again after 30 seconds
});

breaker.on('open', () => console.log('Circuit OPENED — stopping requests'));
breaker.on('halfOpen', () => console.log('Circuit HALF-OPEN — testing'));
breaker.on('close', () => console.log('Circuit CLOSED — back to normal'));

// Fallback when circuit is open
breaker.fallback(() => ({
  status: 'queued',
  message: 'Payment service temporarily unavailable. Your order is queued.'
}));

// Use in your route
app.post('/api/pay', async (req, res) => {
  const result = await breaker.fire(req.body);
  res.json(result);
});
```

### 75. What are pre-signed URLs and when would you use them for file uploads?
**Problem:** Uploading files through your server uses your server's bandwidth and memory.
**Solution:** Pre-signed URLs let the client upload directly to cloud storage (S3), bypassing your server.

**Flow:**
1. Client asks your server "I want to upload a file"
2. Server generates a pre-signed URL (valid for e.g., 5 minutes) from S3
3. Server sends the URL back to the client
4. Client uploads directly to S3 using the pre-signed URL
5. S3 notifies your server (via webhook or client confirmation)

```javascript
const { S3Client, PutObjectCommand } = require('@aws-sdk/client-s3');
const { getSignedUrl } = require('@aws-sdk/s3-request-presigner');

const s3 = new S3Client({ region: 'ap-south-1' });

app.post('/api/upload/presigned-url', authenticate, async (req, res) => {
  const { fileName, fileType } = req.body;

  // Validate file type
  const allowedTypes = ['image/jpeg', 'image/png', 'image/webp'];
  if (!allowedTypes.includes(fileType)) {
    return res.status(400).json({ error: 'Invalid file type' });
  }

  const key = `uploads/${req.user._id}/${Date.now()}-${fileName}`;

  const command = new PutObjectCommand({
    Bucket: process.env.S3_BUCKET,
    Key: key,
    ContentType: fileType,
  });

  const presignedUrl = await getSignedUrl(s3, command, { expiresIn: 300 }); // 5 min

  res.json({ uploadUrl: presignedUrl, key });
});
```

**Benefits:**
- Server doesn't handle file data — saves bandwidth and memory
- Supports large files without server timeout issues
- S3 handles storage, CDN, replication automatically
- Secure — URL expires, only allows the specified operation
