A1. GLOBAL INTERPRETER LOCK (GIL)
──────────────────────────────────
The GIL is a mutex in CPython that ensures only one thread executes Python
bytecode at a time. It exists because CPython's memory management (reference
counting) is not thread-safe.

Implications for backends:
- I/O-bound tasks: GIL is released during I/O (network, disk). Threading still
  provides concurrency for web servers handling many simultaneous requests.
- CPU-bound tasks: True parallelism is NOT achieved. Threads take turns.
  Use multiprocessing or asyncio instead.
- Workarounds: Use ProcessPoolExecutor for CPU-heavy tasks, use asyncio for
  high-concurrency I/O-bound workloads, or use Cython/C extensions that
  release the GIL.
- Note: PyPy and Jython do NOT have a GIL, but CPython is the standard.

Example: A Django app with Gunicorn uses multiple processes (not threads)
to bypass the GIL for true parallelism.

A2. DEEP COPY vs SHALLOW COPY
──────────────────────────────
- Shallow copy: Creates a new object, but references to nested objects remain
  shared. Use copy.copy() or slicing (list[:]).
- Deep copy: Creates a fully independent clone of the object and all nested
  objects. Use copy.deepcopy().

Example:
  import copy
  original = {"a": [1, 2, 3]}
  shallow = copy.copy(original)
  shallow["a"].append(4)       # Also modifies original["a"]!

  deep = copy.deepcopy(original)
  deep["a"].append(5)          # Does NOT modify original

Backend use case:
- Shallow: When you need a quick copy of a flat config dictionary.
- Deep: When cloning a complex object graph (e.g., a pipeline configuration)
  to avoid accidental mutation between requests.

A3. PYTHON MEMORY MANAGEMENT
──────────────────────────────
Python uses two mechanisms:

1. Reference Counting: Every object has a counter. When it reaches 0, the
   memory is immediately freed. Use sys.getrefcount(obj) to inspect.

2. Garbage Collector (gc module): Handles reference cycles (A → B → A).
   It uses generational garbage collection (3 generations) to identify and
   break cycles. Run with gc.collect().

Reference cycle example:
  a = []
  b = [a]
  a.append(b)  # a <-> b cycle; neither will be freed by refcount alone

Best practices: Use weak references (weakref module) to avoid unintentional
reference cycles in caches and observers.

A4. DECORATORS
───────────────
A decorator is a higher-order function that wraps another function to extend
its behavior without modifying it.

Example 1 — Execution timer:
  import time
  import functools

  def timer(func):
      @functools.wraps(func)
      def wrapper(*args, **kwargs):
          start = time.perf_counter()
          result = func(*args, **kwargs)
          elapsed = time.perf_counter() - start
          print(f"{func.__name__} took {elapsed:.4f}s")
          return result
      return wrapper

Example 2 — Retry decorator:
  def retry(max_attempts=3, delay=1.0):
      def decorator(func):
          @functools.wraps(func)
          def wrapper(*args, **kwargs):
              for attempt in range(max_attempts):
                  try:
                      return func(*args, **kwargs)
                  except Exception as e:
                      if attempt == max_attempts - 1:
                          raise
                      time.sleep(delay)
          return wrapper
      return decorator

Always use @functools.wraps to preserve the original function's metadata.

A5. *args AND **kwargs
──────────────────────
- *args: Collects positional arguments into a tuple.
- **kwargs: Collects keyword arguments into a dictionary.

  def log_event(event_type, *args, **kwargs):
      print(f"Event: {event_type}, Args: {args}, Meta: {kwargs}")

  log_event("click", "button1", user_id=42, session="abc")

They allow flexible function signatures and are heavily used in middleware,
decorators, and base class method calls (super().__init__(*args, **kwargs)).

A6. GENERATORS & ITERATORS
───────────────────────────
- Iterator: An object with __iter__() and __next__() methods.
- Generator: A function using yield to produce values lazily (one at a time).

  def read_large_file(path):
      with open(path) as f:
          for line in f:
              yield line.strip()   # Only one line in memory at a time

Benefits: Memory-efficient; ideal for streaming large datasets, ETL pipelines,
or paginating API responses without loading everything into RAM.

Generator expression: (x*2 for x in range(1_000_000))  # No list in memory

A7. PYTHON DATA MODEL & DUNDER METHODS
────────────────────────────────────────
Dunder methods let you define how objects behave with Python syntax.

Common ones:
  __init__    → constructor
  __repr__    → developer-facing string (used in logs/debuggers)
  __str__     → user-facing string
  __len__     → len(obj)
  __getitem__ → obj[key]
  __contains__→ "x" in obj
  __eq__      → obj1 == obj2
  __hash__    → hash(obj), needed for dict keys and set members
  __enter__ / __exit__ → context manager (with statement)
  __call__    → make instances callable

Example:
  class Vector:
      def __init__(self, x, y):
          self.x, self.y = x, y
      def __add__(self, other):
          return Vector(self.x + other.x, self.y + other.y)
      def __repr__(self):
          return f"Vector({self.x}, {self.y})"

A8. STATICMETHOD vs CLASSMETHOD vs INSTANCE METHOD
────────────────────────────────────────────────────
- Instance method: Has access to the instance (self). Most common.
- @classmethod: Has access to the class (cls), not the instance.
  Use for alternative constructors or factory methods.
- @staticmethod: No access to self or cls. Just a utility function
  logically grouped inside the class.

  class Date:
      def __init__(self, year, month, day):
          self.year, self.month, self.day = year, month, day

      @classmethod
      def from_string(cls, date_str):
          y, m, d = map(int, date_str.split("-"))
          return cls(y, m, d)   # Alternative constructor

      @staticmethod
      def is_valid(date_str):
          parts = date_str.split("-")
          return len(parts) == 3  # Pure utility

A9. METACLASSES
────────────────
A metaclass is the class of a class. Just as an object is an instance of
a class, a class is an instance of a metaclass. The default metaclass is `type`.

Use cases for backend developers:
- Auto-registering plugin classes (e.g., command pattern)
- Enforcing interface contracts at class definition time
- Adding logging or validation to all methods automatically
- ORM systems (Django models use metaclasses internally)

  class SingletonMeta(type):
      _instances = {}
      def __call__(cls, *args, **kwargs):
          if cls not in cls._instances:
              cls._instances[cls] = super().__call__(*args, **kwargs)
          return cls._instances[cls]

  class Database(metaclass=SingletonMeta):
      pass

Use sparingly — metaclasses add complexity. Decorators or __init_subclass__
are simpler alternatives for most cases.

A10. MUTABLE vs IMMUTABLE TYPES
────────────────────────────────
Immutable: int, float, str, tuple, frozenset, bytes — cannot be changed after
creation. They are hashable and can be dictionary keys or set members.

Mutable: list, dict, set — can be modified in place. They are NOT hashable by
default and cannot be used as dictionary keys.

Why it matters:
  - Default mutable arguments are a classic Python bug:
    def add_item(item, lst=[]):  # BAD: lst persists between calls!
        lst.append(item)
        return lst
  - Fix: def add_item(item, lst=None): lst = lst or []

A11. LEGB RULE (VARIABLE SCOPE)
────────────────────────────────
Python resolves variable names in this order:
  L → Local (inside the current function)
  E → Enclosing (outer function in nested functions)
  G → Global (module-level)
  B → Built-in (Python's built-in names like len, print)

  x = "global"
  def outer():
      x = "enclosing"
      def inner():
          x = "local"
          print(x)   # prints "local"
      inner()

Use `global` keyword to modify a global variable inside a function.
Use `nonlocal` to modify an enclosing variable from a nested function.

A12. CONTEXT MANAGERS
──────────────────────
Context managers implement __enter__ and __exit__ to manage resources.

Class-based:
  class DBConnection:
      def __enter__(self):
          self.conn = create_connection()
          return self.conn
      def __exit__(self, exc_type, exc_val, exc_tb):
          self.conn.close()
          return False   # Don't suppress exceptions

contextlib-based (simpler):
  from contextlib import contextmanager

  @contextmanager
  def db_connection():
      conn = create_connection()
      try:
          yield conn
      finally:
          conn.close()

Backend uses: Managing DB connections, file handles, locks, transactions.

A13. is vs ==
──────────────
- == checks VALUE equality (calls __eq__)
- is checks IDENTITY (same object in memory, same id())

  a = [1, 2, 3]
  b = [1, 2, 3]
  a == b  → True   (same values)
  a is b  → False  (different objects)

  x = None
  x is None → True  (correct way to check for None)
  x == None → works, but is is preferred and faster

A14. COMPREHENSIONS & GENERATOR EXPRESSIONS
─────────────────────────────────────────────
  # List comprehension — creates full list in memory
  squares = [x**2 for x in range(1000)]

  # Dict comprehension
  mapping = {k: v for k, v in zip(keys, values)}

  # Generator expression — lazy; does not store all values
  total = sum(x**2 for x in range(1_000_000))

When to use what:
  - Need all results at once → list comprehension
  - One-pass consumption (sum, any, all) → generator expression
  - Memory is a concern (large data) → generator
  - Building a lookup table → dict comprehension

A15. BUILT-IN DATA STRUCTURES & TIME COMPLEXITIES
───────────────────────────────────────────────────
  Data Structure  | Access  | Search  | Insert  | Delete
  ─────────────── | ─────── | ─────── | ─────── | ───────

A16. FOUR PILLARS OF OOP
─────────────────────────
1. Encapsulation: Bundling data and methods; hiding internals with _ and __.
   class BankAccount:
       def __init__(self): self.__balance = 0
       def deposit(self, amt): self.__balance += amt

2. Inheritance: Child classes inherit from parent.
   class Animal:
       def speak(self): raise NotImplementedError
   class Dog(Animal):
       def speak(self): return "Woof"

3. Polymorphism: Same interface, different implementations.
   def make_speak(animal): print(animal.speak())  # Works for Dog, Cat, etc.

4. Abstraction: Hiding implementation details via abstract classes/interfaces.
   from abc import ABC, abstractmethod
   class Shape(ABC):
       @abstractmethod
       def area(self): pass

A17. METHOD RESOLUTION ORDER (MRO) & MULTIPLE INHERITANCE
───────────────────────────────────────────────────────────
Python uses C3 linearization to determine MRO — the order in which base
classes are searched when looking up a method.

  class A: pass
  class B(A): pass
  class C(A): pass
  class D(B, C): pass

  print(D.__mro__)  # D → B → C → A → object

The C3 algorithm ensures:
  - Child before parent
  - Left-to-right among siblings
  - Each class appears only once

Use super() to delegate to the next class in MRO, enabling cooperative
multiple inheritance.

───────────────────────────────────────────────────────────────────────────────

A18. ABSTRACT BASE CLASSES (ABCs)
───────────────────────────────────
ABCs enforce that subclasses implement specific methods.

  from abc import ABC, abstractmethod

  class PaymentProcessor(ABC):
      @abstractmethod
      def charge(self, amount: float) -> bool: ...

      @abstractmethod
      def refund(self, transaction_id: str) -> bool: ...

  class StripeProcessor(PaymentProcessor):
      def charge(self, amount): return stripe.charge(amount)
      def refund(self, tid): return stripe.refund(tid)

  PaymentProcessor()  # TypeError! Cannot instantiate ABC directly.

ABCs also allow isinstance() checks without requiring direct inheritance
(by registering virtual subclasses).

A19. COMPOSITION vs INHERITANCE
─────────────────────────────────
Inheritance: "IS-A" relationship. Use when the subclass truly IS a type of
the parent and shares most behavior.

Composition: "HAS-A" relationship. The class contains an instance of another
class. More flexible; avoids the fragile base class problem.

  # Inheritance (can be rigid)
  class Logger(BaseLogger): pass

  # Composition (preferred for flexibility)
  class OrderService:
      def __init__(self, db, logger, payment):
          self.db = db
          self.logger = logger
          self.payment = payment

Rule of thumb: Favor composition over inheritance (Gang of Four principle).
Use inheritance for type hierarchies; composition for behavior reuse.

A21. __slots__
───────────────
By default, Python stores instance attributes in a __dict__ (dictionary).
__slots__ replaces this with a fixed-size array, reducing memory overhead.

  class Point:
      __slots__ = ("x", "y")
      def __init__(self, x, y):
          self.x, self.y = x, y

Benefits: ~30-50% less memory per instance, slightly faster attribute access.
Drawbacks: Cannot add arbitrary attributes; makes multiple inheritance tricky.

Use when: Creating millions of instances (e.g., parsing large datasets).

A22. SINGLETON PATTERN
───────────────────────
  # Thread-safe Singleton using a metaclass
  import threading

  class SingletonMeta(type):
      _instances = {}
      _lock = threading.Lock()

      def __call__(cls, *args, **kwargs):
          with cls._lock:
              if cls not in cls._instances:
                  cls._instances[cls] = super().__call__(*args, **kwargs)
          return cls._instances[cls]

  class Config(metaclass=SingletonMeta):
      def __init__(self):
          self.settings = {}

Alternatives: Module-level constants (Python modules are already singletons),
or dependency injection (preferred in testable code).

A24. ASYNCIO EVENT LOOP
────────────────────────
The event loop is a single-threaded scheduler that manages coroutines.
It runs one coroutine at a time, but switches between them when they await
(suspend) on I/O or other async operations.

Internal flow:
  1. Start event loop (asyncio.run())
  2. Schedule coroutines as Tasks
  3. Poll for I/O readiness (using selectors/epoll/kqueue)
  4. Resume coroutines when their awaited result is ready
  5. Repeat until all tasks complete

This enables handling thousands of connections without spawning thousands
of threads, making it very memory-efficient.

A25. async / await / COROUTINES
─────────────────────────────────
  async def fetch_data(url: str) -> dict:
      async with aiohttp.ClientSession() as session:
          async with session.get(url) as response:
              return await response.json()

  # Run multiple concurrently (not sequentially)
  async def main():
      results = await asyncio.gather(
          fetch_data("http://api1.com"),
          fetch_data("http://api2.com"),
          fetch_data("http://api3.com"),
      )

A26. RACE CONDITIONS & DEADLOCKS
──────────────────────────────────
Race Condition: Two threads access shared data simultaneously, leading to
inconsistent results.
  Fix: Use threading.Lock()
  lock = threading.Lock()
  with lock:
      shared_counter += 1

Deadlock: Thread A holds Lock 1 and waits for Lock 2; Thread B holds Lock 2
and waits for Lock 1. Neither can proceed.
  Prevention:
  - Always acquire locks in the same order
  - Use timeouts: lock.acquire(timeout=5)
  - Use threading.RLock() for reentrant locking

Semaphore: Limits concurrent access to N (not just 1).
  sem = threading.Semaphore(5)  # Max 5 threads at once

A27. PRODUCER-CONSUMER PATTERN
────────────────────────────────
  import threading, queue

  def producer(q):
      for i in range(10):
          q.put(i)        # Blocks if queue is full
      q.put(None)         # Sentinel to signal done

  def consumer(q):
      while True:
          item = q.get()  # Blocks until item available
          if item is None:
              break
          process(item)
          q.task_done()

  q = queue.Queue(maxsize=5)
  t1 = threading.Thread(target=producer, args=(q,))
  t2 = threading.Thread(target=consumer, args=(q,))
  t1.start(); t2.start()
  t1.join(); t2.join()

A28. concurrent.futures
────────────────────────
High-level abstraction over threading and multiprocessing.

  from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

  # I/O-bound: use threads
  with ThreadPoolExecutor(max_workers=10) as executor:
      futures = [executor.submit(fetch_url, url) for url in urls]
      results = [f.result() for f in futures]

  # CPU-bound: use processes
  with ProcessPoolExecutor(max_workers=4) as executor:
      results = list(executor.map(cpu_heavy_fn, data_chunks))

A29. asyncio I/O vs CPU & run_in_executor
──────────────────────────────────────────
asyncio is excellent for I/O-bound tasks but blocks on CPU-bound ones
(since it's single-threaded).

Solution for CPU-bound tasks in an async context:
  loop = asyncio.get_event_loop()
  result = await loop.run_in_executor(None, cpu_heavy_function, arg)
  # None uses the default ThreadPoolExecutor
  # For CPU tasks: pass a ProcessPoolExecutor instead

A30. BACKPRESSURE
──────────────────
Backpressure occurs when a producer generates data faster than a consumer
can process it. Without it, queues grow unboundedly, leading to OOM errors.

Strategies:
- Bounded queues: asyncio.Queue(maxsize=100) — blocks producer when full
- Rate limiting: Use asyncio.Semaphore to cap concurrent tasks
- Flow control signals: Producer monitors queue size; slows down if needed
- Drop policies: Drop oldest items or reject new ones with 503 Too Busy

A32. DJANGO REQUEST-RESPONSE CYCLE
────────────────────────────────────
1. HTTP request hits the WSGI/ASGI server (Gunicorn/Uvicorn)
2. Django's WSGIHandler receives it
3. Request passes through MIDDLEWARE (in order): SecurityMiddleware,
   SessionMiddleware, AuthenticationMiddleware, etc.
4. URL dispatcher (urls.py) matches the path via regex/path() patterns
5. View function/class is called with the request object
6. View queries DB, processes logic, builds context
7. Template is rendered (or DRF serializes JSON)
8. Response passes back through MIDDLEWARE (in reverse)
9. Response sent back to client

───────────────────────────────────────────────────────────────────────────────

A33. DJANGO ORM & N+1 PROBLEM
───────────────────────────────
The N+1 problem: A query fetches N records, then for each record fires
an additional query — resulting in N+1 total queries.

  # BAD — N+1 queries
  books = Book.objects.all()
  for book in books:
      print(book.author.name)  # Separate query per book!

  # GOOD — 2 queries total
  books = Book.objects.select_related("author").all()  # JOIN

  # For many-to-many or reverse FK
  books = Book.objects.prefetch_related("tags").all()

Detection: Use django-debug-toolbar or log queries via:
  from django.db import connection; print(connection.queries)

A34. DJANGO MIDDLEWARE
───────────────────────
Middleware sits between the request and the view/response. It processes
ALL requests and responses globally.

Custom middleware (new-style):
  class RequestLogMiddleware:
      def __init__(self, get_response):
          self.get_response = get_response

      def __call__(self, request):
          # Code before the view
          start = time.time()
          response = self.get_response(request)
          # Code after the view
          duration = time.time() - start
          logger.info(f"{request.method} {request.path} — {duration:.3f}s")
          return response

Register in settings.py: MIDDLEWARE = [..., "myapp.middleware.RequestLogMiddleware"]

A35. DJANGO SIGNALS
────────────────────
Signals allow decoupled components to be notified when certain actions occur.

  from django.db.models.signals import post_save
  from django.dispatch import receiver

  @receiver(post_save, sender=User)
  def send_welcome_email(sender, instance, created, **kwargs):
      if created:
          send_email(instance.email, "Welcome!")

Built-in signals: pre_save, post_save, pre_delete, post_delete, m2m_changed.

When to USE: Cross-cutting concerns (audit logs, notifications).
When to AVOID: When the logic is tightly coupled to the model — use
save() override instead. Signals make code harder to trace and test.

A36. FASTAPI DEPENDENCY INJECTION
───────────────────────────────────
FastAPI's Depends() system allows injecting shared resources into endpoints.

  from fastapi import Depends, FastAPI
  from sqlalchemy.orm import Session

  def get_db():
      db = SessionLocal()
      try:
          yield db    # Provides the session
      finally:
          db.close()  # Cleans up after the request

  @app.get("/users/{user_id}")
  def get_user(user_id: int, db: Session = Depends(get_db)):
      return db.query(User).filter(User.id == user_id).first()

Dependencies can be nested, cached (use_cache=True), and async.
They handle: DB sessions, authentication, rate limiting, feature flags.

A38. JWT AUTHENTICATION
────────────────────────
JSON Web Tokens encode user identity as a signed token (header.payload.signature).

  import jwt
  from datetime import datetime, timedelta

  SECRET = "your-secret-key"
  ALGORITHM = "HS256"

  def create_token(user_id: int) -> str:
      payload = {
          "sub": str(user_id),
          "exp": datetime.utcnow() + timedelta(hours=1)
      }
      return jwt.encode(payload, SECRET, algorithm=ALGORITHM)

  def verify_token(token: str) -> dict:
      return jwt.decode(token, SECRET, algorithms=[ALGORITHM])

FastAPI integration: Use HTTPBearer security scheme + Depends() to protect routes.
Best practices: Short expiry for access tokens; use refresh tokens for longevity;
store secrets in env vars, NOT in code.

A41. REST PRINCIPLES
──────────────────────
1. Statelessness: Each request contains all info the server needs. No session.
2. Client-Server separation: UI and backend evolve independently.
3. Uniform interface: Resource-based URLs, standard HTTP methods, HATEOAS.
4. Cacheability: Responses should indicate if they can be cached.
5. Layered system: Client doesn't know if it's talking to a proxy or server.

Idempotency:
  GET, PUT, DELETE → idempotent (same result no matter how many times called)
  POST → NOT idempotent (creates a new resource each time)
  PATCH → depends on implementation

Resource-based URLs:
  GOOD: GET /users/42/orders
  BAD:  GET /getUserOrders?userId=42

A43. API VERSIONING
─────────────────────
1. URL versioning: /api/v1/users (most common; easy to test in browser)
2. Header versioning: Accept: application/vnd.myapi.v1+json
3. Query param: /api/users?version=1 (least preferred)

Best practice: Use URL versioning for public APIs. Maintain at least one
old version while deprecating. Send Deprecation headers to warn consumers.

A44. RATE LIMITING
───────────────────
Algorithms:
  - Token Bucket: Tokens refill at a fixed rate. Burst-friendly.
  - Fixed Window: Count requests per time window (e.g., 100/minute).
  - Sliding Window: More accurate; counts over a rolling window.
  - Leaky Bucket: Smooths burst traffic into a steady stream.

Python implementation:
  - Django: Use django-ratelimit or djangorestframework
  - FastAPI: Use slowapi (based on limits library)
  - Redis-based: Store counters in Redis for distributed rate limiting.

Response: Return 429 Too Many Requests with Retry-After header.

───────────────────────────────────────────────────────────────────────────────

A47. PAGINATION
────────────────
1. Offset-based: ?page=3&limit=20 — simple but slow for large datasets
   (DB must scan offset rows before fetching)

2. Cursor-based: ?cursor=eyJ... — uses an opaque cursor (encoded ID or
   timestamp). Fast even on millions of rows. Does not allow jumping to
   arbitrary pages.

3. Keyset pagination: ?after_id=500&limit=20 — uses WHERE id > 500.
   Efficient, stable (doesn't shift if rows are deleted), but cursor must
   be unique and ordered.

Best for large datasets: Cursor or keyset pagination.
Best for simple use cases: Offset.

A50. DATABASE INDEXES
──────────────────────
An index is a data structure (B-tree, hash) that speeds up lookups at the
cost of extra storage and slower writes.

When to add indexes:
  - Columns used in WHERE, JOIN, ORDER BY, GROUP BY
  - Foreign keys
  - Columns with high cardinality

When indexes HURT:
  - Heavy write tables (insert/update must also update indexes)
  - Low-cardinality columns (e.g., boolean — index rarely helps)
  - Very small tables (full scan is faster)

Types:
  - Single-column: most common
  - Composite (multi-column): efficient for multi-column queries
  - Partial: index only a subset (WHERE is_active = TRUE)
  - Unique: enforces uniqueness + speeds up lookups

───────────────────────────────────────────────────────────────────────────────

A51. TRANSACTIONS & ACID
─────────────────────────
  A - Atomicity: All-or-nothing. Either all operations succeed or none do.
  C - Consistency: DB moves from one valid state to another.
  I - Isolation: Concurrent transactions don't interfere with each other.
  D - Durability: Committed data persists even after a crash.

Django transactions:
  from django.db import transaction

  with transaction.atomic():
      account.balance -= amount
      ledger.create(amount=amount)
      # Rolls back BOTH if any exception is raised

Isolation levels (SQL standard):
  READ UNCOMMITTED → READ COMMITTED → REPEATABLE READ → SERIALIZABLE
  (lower isolation = better performance but more anomalies)

───────────────────────────────────────────────────────────────────────────────

A53. DATABASE MIGRATIONS IN PRODUCTION
────────────────────────────────────────
Safe migration practices:
1. Backward-compatible migrations first: Add new column (nullable first),
   deploy code, then backfill, then add NOT NULL constraint.
2. Avoid locking large tables: Use CONCURRENTLY for index creation in Postgres.
3. Never rename columns/tables directly (breaks running code).
4. Use zero-downtime migration patterns: expand (add new), migrate data,
   contract (remove old) — in separate deployments.
5. Always test migrations on a production-size staging database.

Django: python manage.py migrate with --fake and --run-syncdb are useful
for complex situations.

A59. CACHING STRATEGIES
─────────────────────────
1. Cache-Aside (Lazy Loading):
   App checks cache → miss → fetch from DB → store in cache.
   Pros: Only caches what's needed. Cons: Cache miss = slow first request.

2. Write-Through:
   On write: update DB AND cache simultaneously.
   Pros: Cache always fresh. Cons: Slower writes, caches unused data.

3. Write-Behind (Write-Back):
   Write to cache, then asynchronously persist to DB.
   Pros: Very fast writes. Cons: Risk of data loss if cache crashes.

4. Read-Through:
   Cache sits in front; on miss, cache (not app) fetches from DB.
   Pros: Simpler app code. Cons: Requires cache library support.

───────────────────────────────────────────────────────────────────────────────

A61. CACHE INVALIDATION STRATEGIES
────────────────────────────────────
Cache invalidation is considered one of the hardest problems in CS.

1. TTL (Time-To-Live): Entries expire automatically after N seconds.
   Simple but stale data possible until expiry.

2. Event-driven: On DB write, publish an event to invalidate specific keys.
   More precise but complex.

3. Cache tags: Tag related keys (e.g., "user_42"), invalidate all by tag.
   Used in Django with django-cache-machine.

4. Versioned keys: Increment a version number; old keys are naturally orphaned.
   user_v3_42 vs user_v2_42.

───────────────────────────────────────────────────────────────────────────────

A63. CACHE STAMPEDE (THUNDERING HERD)
───────────────────────────────────────
Problem: Many requests arrive simultaneously for an expired cache key.
All miss and hit the DB at once, causing a spike.

Solutions:
1. Mutex/lock: First request fetches from DB and populates cache;
   others wait. Use Redis SET NX (set if not exists) as a distributed lock.

2. Probabilistic early expiration: Start refreshing the cache slightly
   before it expires, randomly, to avoid simultaneous expiry.

3. Stale-while-revalidate: Serve stale data while refreshing in the background.

4. Background refresh: A scheduled job refreshes popular keys proactively.

A65. CELERY
────────────
Celery is a distributed task queue for Python.

Components:
  - Task: A Python function decorated with @app.task
  - Worker: Process that consumes and executes tasks
  - Broker: Message transport (Redis, RabbitMQ). Stores task messages.
  - Result Backend: Stores task results (Redis, DB, Memcached)

  from celery import Celery
  app = Celery("myapp", broker="redis://localhost/0")

  @app.task(bind=True, max_retries=3)
  def send_email(self, user_id):
      try:
          email_service.send(user_id)
      except Exception as exc:
          raise self.retry(exc=exc, countdown=60)

  # From your Django view:
  send_email.delay(user_id=42)

A67. CELERY RETRIES & DEAD-LETTER QUEUES
──────────────────────────────────────────
  @app.task(
      bind=True,
      max_retries=5,
      default_retry_delay=60,        # 60s between retries
      autoretry_for=(NetworkError,), # Auto-retry on these exceptions
      retry_backoff=True,            # Exponential backoff
      retry_jitter=True,             # Random jitter to avoid thundering herd
  )
  def process_payment(self, payment_id):
      ...

Dead-letter queue (DLQ): Route failed tasks (exhausted retries) to a
separate queue for inspection and manual reprocessing.
  In RabbitMQ: Configure x-dead-letter-exchange on the task queue.
  In Redis: Implement a separate "failed" queue manually.

A69. MESSAGE DELIVERY SEMANTICS
─────────────────────────────────
1. At-most-once: Fire and forget. Message may be lost. No redelivery.
   Use: Non-critical notifications.

2. At-least-once: Message delivered one or more times (duplicates possible).
   Use: Most task queues (Celery default). Consumers must be idempotent.

3. Exactly-once: Message delivered exactly once. Very hard to achieve.
   Requires two-phase commit or idempotency keys + deduplication.
   Kafka supports exactly-once semantics with transactional producers.

A79. SQL INJECTION PREVENTION
───────────────────────────────
Never concatenate user input into SQL:
  # DANGEROUS
  cursor.execute(f"SELECT * FROM users WHERE name = '{name}'")

  # SAFE (parameterized query)
  cursor.execute("SELECT * FROM users WHERE name = %s", (name,))

ORMs (Django ORM, SQLAlchemy) use parameterized queries automatically.
Only raw SQL (cursor.execute with format strings) is dangerous.

───────────────────────────────────────────────────────────────────────────────

A81. SECURE PASSWORD STORAGE
──────────────────────────────
NEVER store plain-text passwords or use MD5/SHA1 (too fast; rainbow tables).

Use adaptive hashing algorithms:
  import bcrypt

  # Hash
  hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))

  # Verify
  bcrypt.checkpw(password.encode(), hashed)

Alternatives: argon2 (winner of Password Hashing Competition), scrypt.
Django uses PBKDF2 by default; switch to argon2 via django[argon2].

Key properties: Slow by design (cost factor), salted (unique per user),
one-way (cannot be reversed).

  Bad practice: Hardcode credentials in source code.
  
  Good practices:
  1. Environment variables: os.environ["DATABASE_URL"]

  3. Cloud secrets managers: AWS Secrets Manager, GCP Secret Manager,

A87. OPTIMIZING SLOW DJANGO QUERYSETS

Components:
- Write API: POST /shorten → generate short code → store in DB
- Read API: GET /{code} → lookup → 301/302 redirect to original URL
- Short code generation: Base62 (a-z,A-Z,0-9) encoding of an auto-increment ID

A94. CIRCUIT BREAKER PATTERN
──────────────────────────────
Prevents cascading failures when a downstream service is unhealthy.

States:
  CLOSED → normal operation (requests pass through)
  OPEN   → service is down; requests fail fast without hitting it
  HALF-OPEN → test with a probe request; if OK, back to CLOSED

Python implementation with pybreaker:
  import pybreaker

  db_breaker = pybreaker.CircuitBreaker(fail_max=5, reset_timeout=30)

  @db_breaker
  def fetch_from_external_service():
      return requests.get("http://external-api.com/data")

Without the circuit breaker, a slow dependency would hold threads/connections,
eventually exhausting the pool and taking down the entire application.

A98. WSGI vs ASGI
──────────────────
WSGI (Web Server Gateway Interface): Synchronous standard. One request at
a time per worker. Used by Django (default) and Flask.
Servers: Gunicorn, uWSGI.

ASGI (Asynchronous Server Gateway Interface): Async standard. Supports
WebSockets, HTTP/2, long-polling, and concurrent connections.
Servers: Uvicorn, Hypercorn, Daphne.

Use ASGI when: Real-time features (WebSockets, SSE), high-concurrency APIs,
or using async frameworks (FastAPI, Django Channels).

Structured logging outputs machine-readable JSON instead of plain strings,

A106. LARGE FILE UPLOAD PROCESSING
────────────────────────────────────
Stream and process line-by-line instead of loading entirely into memory:

  import csv
  import io

  async def process_upload(file: UploadFile):
      content = await file.read()               # Read once
      stream = io.StringIO(content.decode())
      reader = csv.DictReader(stream)
      
      for chunk in chunked(reader, size=1000):  # Process in batches
          await bulk_insert(chunk)              # DB batch insert

  def chunked(iterable, size):
      batch = []
      for row in iterable:
          batch.append(row)
          if len(batch) == size:
              yield batch
              batch = []
      if batch:
          yield batch

For very large files: stream directly to S3, then process asynchronously
with a Celery task.

A107. REPOSITORY PATTERN
─────────────────────────
Abstracts the data access layer from business logic.

  # Repository interface
  class UserRepository(ABC):
      @abstractmethod
      def get_by_id(self, user_id: int) -> User: ...
      @abstractmethod
      def save(self, user: User) -> None: ...

  # Implementation
  class SQLUserRepository(UserRepository):
      def __init__(self, db: Session):
          self.db = db
      def get_by_id(self, user_id):
          return self.db.query(User).filter_by(id=user_id).first()
      def save(self, user):
          self.db.add(user); self.db.commit()

  # Service uses the abstraction
  class UserService:
      def __init__(self, repo: UserRepository):
          self.repo = repo

Benefits: Easy to swap DB implementations; business logic is fully testable
without a real database (just inject a mock repo).

A109. SOLID PRINCIPLES
───────────────────────
S — Single Responsibility: A class should have only one reason to change.
    Bad: UserService handles auth, email, and DB.
    Good: Split into AuthService, EmailService, UserRepository.

O — Open/Closed: Open for extension, closed for modification.
    Use inheritance or composition to add behavior without editing existing code.

L — Liskov Substitution: Subclasses must be substitutable for their base class.
    A subclass should not weaken preconditions or strengthen postconditions.

I — Interface Segregation: Many specific interfaces > one general-purpose one.
    Don't force a class to implement methods it doesn't need.

D — Dependency Inversion: Depend on abstractions, not concrete classes.
    Inject dependencies (DB session, email client) rather than instantiating
    them inside the class.

A110. SYNCHRONOUS vs EVENT-DRIVEN ARCHITECTURE
───────────────────────────────────────────────
Synchronous (Request-Response):
  - Service A calls Service B and waits for a response.
  - Simple, easy to trace, tight coupling.
  - Problem: Cascading failures; Service A is blocked while B processes.

Event-Driven:
  - Service A publishes an event; Service B consumes it independently.
  - Loose coupling; services can scale independently.
  - Patterns: Event sourcing, CQRS, Saga pattern for distributed transactions.
  - Tools: Kafka, RabbitMQ, AWS SNS/SQS, Celery.

When to choose event-driven:
  - Long-running operations (order processing, video encoding)
  - Fan-out scenarios (one event → many consumers)
  - Decoupled microservices needing resilience
  - Audit trail requirements (event sourcing)

When to keep synchronous:
  - Simple CRUD APIs
  - When immediate consistency is required
  - Small teams where observability complexity outweighs benefits
